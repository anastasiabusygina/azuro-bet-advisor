## Конфигурация модульной системы

### Выбор модульной системы

В проекте используется **NodeNext** в качестве модульной системы.

Причины выбора:
- Поддержка современного синтаксиса импорта/экспорта ES модулей
- Лучшая совместимость с последними версиями Node.js
- Корректное разрешение путей для файлов TypeScript и JavaScript
- Возможность использования алиасов путей через "paths" в tsconfig.json

### Конфигурация tsconfig.json

Для всех tsconfig.json файлов в проекте используются следующие настройки модулей:

```json
{
  "compilerOptions": {
    "module": "NodeNext",
    "moduleResolution": "NodeNext"
  }
}
```

### Особенности и ограничения

1. **Импорт файлов**: При использовании NodeNext необходимо указывать расширения при импорте JavaScript файлов
   ```typescript
   // Правильно
   import { something } from './module.js';
   
   // Неправильно
   import { something } from './module';
   ```

2. **Типы модулей**: Для TypeScript файлов рекомендуется использовать `.ts` расширения без явного указания
   ```typescript
   // Правильно
   import { something } from './module';
   
   // Также работает
   import { something } from './module.ts';
   ```

3. **package.json**: Добавьте поле `"type": "module"` для использования ESM в .js файлах, или сохраните существующее поведение без него

4. **Конфликты с внешними библиотеками**: Некоторые старые библиотеки могут быть несовместимы с NodeNext, и потребуют дополнительной настройки или помощи transpiler'а

### Структура файлов конфигурации

Проект имеет следующие конфигурационные файлы с указанными параметрами модулей:

1. **Корневой tsconfig.json**: 
   - module: "NodeNext"
   - moduleResolution: "NodeNext"

2. **src/scripts/tsconfig.json**: 
   - module: "NodeNext" 
   - moduleResolution: "NodeNext"

3. **tests/tsconfig.json**: 
   - module: "NodeNext"
   - moduleResolution: "NodeNext"

4. **babel.config.js**: поддерживает импорты с использованием путей из tsconfig

## Управление путями импорта

### Алиасы путей

В проекте настроены следующие алиасы для удобства импорта:

```json
"paths": {
  "@/*": ["src/*"],
  "@models/*": ["src/models/*"],
  "@utils/*": ["src/utils/*"],
  "@scripts/*": ["src/scripts/*"],
  "@tests/*": ["tests/*"],
  "@config/*": ["src/config/*"]
}
```

Использование алиасов:

```typescript
// Импорт с использованием алиаса
import { someUtil } from '@utils/helper';

// Вместо относительного пути
import { someUtil } from '../../../utils/helper';
```

### Индексные файлы

Для удобства импортов в каждой директории созданы индексные файлы:

- `src/utils/index.ts` - экспортирует все утилиты
- `src/models/index.ts` - экспортирует все модели
- `src/scripts/index.ts` - экспортирует все скрипты

Использование индексных файлов:

```typescript
// Импорт всех утилит через индексный файл
import { utilA, utilB, utilC } from '@utils';

// Вместо отдельных импортов
import { utilA } from '@utils/utilA';
import { utilB } from '@utils/utilB';
import { utilC } from '@utils/utilC';
```

## Рекомендации для разработчиков

1. Используйте относительные импорты для файлов внутри одного модуля
2. Используйте алиасы путей для импорта между модулями (`@utils/`, `@models/` и т.д.)
3. При добавлении новых библиотек проверяйте их совместимость с модульной системой NodeNext
4. Избегайте смешивания различных стилей импорта в одном файле
5. Основная бизнес-логика должна находиться в директории `src/scripts/`
6. Используйте мост `src/scripts-bridge` только для интеграции устаревшей функциональности, которая еще не мигрирована
7. Все тесты для бизнес-логики размещайте в `src/scripts/__tests__`
8. Используйте индексные файлы для упрощения импортов
9. Для запуска тестов используйте команду `npm run test:all`
10. Избегайте захардкоженных значений в коде. Используйте значения из конфигурации или библиотеки `@azuro-org/dictionaries` для маппинга
11. Все константы и маппинги должны быть документированы и централизованы
12. При работе с интерфейсными элементами (кнопки, названия ставок) всегда используйте официальные методы из библиотеки Azuro

## Работа с тестами

### Структура тестов

```
/
├── tests/                      # Основные тесты проекта (глобальные тесты)
│   ├── configValidation.test.ts # Тесты валидации конфигурации
│   ├── README.md               # Документация по тестам
│   └── ...
└── src/
    └── scripts/                # Скрипты проекта и основная бизнес-логика
        ├── __tests__/          # Тесты для скриптов (модульные тесты)
        │   ├── getMatchButtons.test.ts
        │   └── ...
        └── ...
```

### Правила организации тестов

1. **Разделение тестов по типам**:
   - **Модульные тесты**: Располагаются в директории `__tests__` рядом с тестируемым кодом
   - **Интеграционные тесты**: Располагаются в директории `tests/` в корне проекта
   - **AST тесты**: Располагаются в директории `tests/ast/`

2. **Именование тестовых файлов**:
   - Все тестовые файлы должны иметь суффикс `.test.ts`
   - Имя файла должно соответствовать имени тестируемого файла
   - Для тестов функциональности: `functionName.test.ts`
   - Для тестов компонентов: `ComponentName.test.ts`
   - Для интеграционных тестов: `feature.integration.test.ts`

3. **Структура модульных тестов**:
   - Тесты для скриптов должны быть организованы в директории `__tests__` внутри директории скриптов
   - Каждый тестовый файл должен соответствовать одному модулю
   - Для каждой публичной функции должно быть написано минимум 2 теста

4. **Структура интеграционных тестов**:
   - Интеграционные тесты размещаются в директории `tests/` в корне проекта
   - Тесты должны быть сгруппированы по функциональности
   - Имена файлов должны заканчиваться на `.integration.test.ts`

5. **Моки и стабы**:
   - Моки для внешних зависимостей должны быть определены в директории `tests/mocks/`
   - Для стандартных моков можно использовать Jest автомоки
   - Все моки должны иметь префикс `mock` или суффикс `.mock.ts`
   - **В модульных тестах необходимо мокировать все внешние зависимости** для обеспечения изоляции тестов
   - **Избегайте мокирования внутренних модулей** тестируемого компонента, это ведет к хрупким тестам

6. **Запуск тестов**:
   - Запуск всех тестов: `npm run test:all`
   - Запуск только модульных тестов: `npm run test`
   - Запуск интеграционных тестов: `npm run test:integration`
   - Запуск тестов для скриптов: `npm run test:scripts`

7. **Организация внутри тестового файла**:
   - Тесты должны быть сгруппированы по функциональности с помощью `describe`
   - Каждый тестовый случай должен быть описан с помощью `it` или `test`
   - Тестовые случаи должны быть независимыми друг от друга
   - Используйте `beforeEach` и `afterEach` для настройки и очистки окружения

8. **Документация тестов**:
   - Каждый тестовый файл должен иметь краткое описание тестируемой функциональности
   - Каждый тестовый случай должен иметь понятное описание
   - Сложная логика в тестах должна быть документирована

### Пример организации теста

```typescript
// src/scripts/__tests__/getMatchButtons.test.ts
import { describe, expect, test, jest, beforeEach } from '@jest/globals';
import { getMatchButtons } from '../getMatchButtons';

describe('getMatchButtons', () => {
  beforeEach(() => {

  });

  test('должен получать данные из GraphQL API', async () => {
    // Тест получения данных из API
  });

  test('должен обрабатывать ошибки подключения к API', async () => {
    // Тест обработки ошибок
  });

  // Другие тестовые случаи
});
```

### Критерии качества тестов

1. **Покрытие кода**: 
   - Целевое покрытие кода - минимум 80%
   - Для критических компонентов - минимум 90%

2. **Изоляция**: 
   - Тесты должны быть изолированы и не зависеть от внешних ресурсов
   - Используйте моки для внешних API и баз данных

3. **Скорость**: 
   - Тесты должны выполняться быстро
   - Тяжелые тесты должны быть помечены как `@slow`

4. **Читаемость**: 
   - Тесты должны быть понятными и служить документацией
   - Используйте говорящие имена для переменных и функций

### Подход к мокированию зависимостей

В проекте применяется следующий подход к мокированию зависимостей:

1. **Модульные тесты**:
   - Мокируйте все внешние зависимости (API, базы данных, файловую систему и т.д.)
   - Избегайте мокирования внутренних компонентов тестируемого модуля
   - Тесты должны проверять поведение модуля, а не его внутреннюю реализацию
   - Проверяйте взаимодействие с внешними зависимостями через проверку вызовов моков

2. **Интеграционные тесты**:
   - Минимизируйте использование моков
   - Тестируйте реальное взаимодействие между компонентами
   - Мокируйте только недоступные в тестовом окружении внешние сервисы
   - Для тестов, требующих реальных внешних сервисов, используйте специальные механизмы пропуска в CI

3. **Баланс между полнотой и изоляцией**:
   - Избегайте чрезмерного мокирования, которое делает тесты оторванными от реальности
   - Однако обеспечивайте достаточную изоляцию для стабильности и скорости тестов
   - При сомнениях предпочитайте тесты, которые проверяют реальное поведение, а не детали реализации

Этот подход обеспечивает баланс между изоляцией тестов для обеспечения их стабильности и проверкой реального поведения модулей.

## Подход к разработке

1. **Модульность**: Каждый файл должен иметь одну ответственность
2. **Повторное использование**: Разрабатывайте код с возможностью повторного использования
3. **Тестируемость**: Пишите тесты для всей бизнес-логики
4. **Изоляция**: Разделяйте бизнес-логику и инфраструктурный код
5. **Прозрачность**: Используйте говорящие имена и документацию

## Работа с конфигурацией

1. Все переменные окружения должны быть валидированы в `src/config.ts`
2. Доступ к переменным окружения должен осуществляться только через конфигурационный слой
3. Тесты `tests/configValidation.test.ts` и `tests/configPresenceValidation.test.ts` проверяют правильность работы с конфигурацией

## Работа с константами и маппингами

1. **Отказ от захардкоженных значений**: Весь код должен избегать "захардкоженных" значений. Вместо этого:
   - Использовать значения из конфигурационных файлов (`config/settings.ts`)
   - Получать специфические для Azuro Protocol значения из библиотеки `@azuro-org/dictionaries`
   - Выносить все константы в отдельные файлы констант

2. **Маппинг интерфейсных элементов**:
   - Для получения названий маркетов (типов ставок) использовать `getMarketName` из библиотеки Azuro
   - Для получения названий кнопок и селекций использовать `getSelectionName` из библиотеки Azuro
   - Пример правильного использования:
   ```typescript
   import { getMarketName, getSelectionName } from '@azuro-org/dictionaries';
   
   // Получение названия рынка из библиотеки вместо хардкода
   const marketName = getMarketName({ marketKey });
   
   // Получение названия исхода из библиотеки вместо хардкода
   const selectionName = getSelectionName({ outcomeId });
   ```

3. **Передача параметров**: Все параметры должны передаваться через:
   - Аргументы командной строки
   - Переменные окружения
   - Конфигурационные файлы

4. **Расширяемость**: Код должен быть написан так, чтобы легко добавлять новые маркеты и исходы без изменения основного кода.

## ⚠️ Изменение кода и тестов с помощью Cursor / ИИ
Во избежание потери смысла и ошибок в логике тестов, изменение кода и тестов должно выполняться в две отдельные итерации:

На первом этапе разрешено менять только рабочий код.
Тесты должны остаться нетронутыми, даже если они временно падают.

На втором этапе анализируются упавшие тесты.
Нейросеть (или разработчик) должна:

- показать список ошибок,

- объяснить, почему тесты больше невалидны (если поведение действительно изменилось),

и только после этого — изменить тесты осознанно.

❗️Тесты не должны автоматически подгоняться под изменившийся код без объяснения причин.

Это позволяет сохранить контроль над контрактами функций, избежать случайных регрессий и обеспечить прозрачность ревью.
