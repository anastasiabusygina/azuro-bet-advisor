# Правила тестирования в проекте Azuro Betting Tools

## Структура тестов

В проекте используется следующая структура тестов:

- `tests/` - глобальные и интеграционные тесты проекта
  - `tests/configValidation.test.ts` - тесты для валидации конфигурации
  - `tests/configPresenceValidation.test.ts` - тесты для проверки наличия необходимых конфигурационных параметров
  - `tests/strictTryCatchValidation.test.ts` - тесты для проверки корректности обработки исключений
  - `tests/utils.ts` - утилиты для тестирования
  - `tests/ast/` - AST тесты для статического анализа кода

- `src/scripts/__tests__/` - модульные тесты для скриптов
  - Каждый тестовый файл соответствует одному модулю
  - Пример: `src/scripts/__tests__/getMatchButtons.test.ts` тестирует `src/scripts/getMatchButtons.ts`

## Типы тестов

1. **Модульные тесты** - тестируют отдельные функции и компоненты в изоляции
   - Располагаются в директории `__tests__` рядом с тестируемым кодом
   - Используют моки для внешних зависимостей
   - Запускаются командой `npm run test`

2. **Интеграционные тесты** - тестируют взаимодействие нескольких компонентов
   - Располагаются в директории `tests/` в корне проекта
   - Имеют суффикс `.integration.test.ts`
   - Запускаются командой `npm run test:integration`

3. **AST тесты** - тестируют структуру кода с помощью статического анализа
   - Располагаются в директории `tests/ast/`
   - Используют TypeScript Compiler API или другие инструменты для анализа кода
   - Запускаются как часть общих тестов

## Правила именования

- **Модульные тесты**: `componentName.test.ts` или `functionName.test.ts`
- **Интеграционные тесты**: `feature.integration.test.ts`
- **AST тесты**: `rule.ast.test.ts`
- **Моки**: `module.mock.ts` или `mockModule.ts`

## Работа с моками

Для моков внешних зависимостей используется следующий подход:

1. **Автоматические моки Jest**:
   ```typescript
   jest.mock('module-name');
   ```

2. **Ручные моки**:
   ```typescript
   jest.mock('module-name', () => ({
     function1: jest.fn(),
     function2: jest.fn()
   }));
   ```

3. **Файловые моки**:
   - Создаются в директории `tests/mocks/`
   - Импортируются в тестах `import { mockFunction } from '../../tests/mocks/mockModule';`

### Правила мокирования

1. **В модульных тестах**:
   - **Необходимо мокировать все внешние зависимости** (API, базы данных, файловую систему)
   - **Избегайте мокирования внутренних компонентов** тестируемого модуля
   - Моки должны быть максимально простыми и понятными
   - Проверяйте как вызовы моков, так и результаты функций

2. **В интеграционных тестах**:
   - Мокируйте только недоступные в тестовом окружении внешние сервисы
   - Акцент на тестировании реального взаимодействия между компонентами

3. **Ключевой принцип баланса**:
   - Достаточное мокирование для изоляции и стабильности тестов
   - Но без чрезмерного мокирования, которое отрывает тесты от реальности
   - При сомнениях предпочитайте тесты, которые проверяют реальное поведение, а не детали реализации

## Организация тестового файла

```typescript
// Импорты
import { describe, expect, test, jest, beforeEach } from '@jest/globals';
import { functionToTest } from '../module';

// Моки
jest.mock('external-dependency');

// Описание тестового набора
describe('Module: functionToTest', () => {
  // Настройка окружения перед каждым тестом
  beforeEach(() => {
    jest.clearAllMocks();
  });

  // Тестовые случаи
  test('should handle normal case', () => {
    // Arrange
    const input = '...';
    
    // Act
    const result = functionToTest(input);
    
    // Assert
    expect(result).toBe(expectedResult);
  });

  test('should handle error case', () => {
    // Тест обработки ошибок
  });
});
```

## Рекомендации по написанию тестов

1. **Используйте подход AAA (Arrange-Act-Assert)**:
   - Arrange: Подготовьте данные и окружение
   - Act: Выполните тестируемую функцию
   - Assert: Проверьте результат

2. **Тестируйте граничные случаи**:
   - Пустые входные данные
   - Максимальные и минимальные значения
   - Недопустимые входные данные

3. **Изолируйте тесты**:
   - Каждый тест должен быть независимым
   - Не должно быть зависимостей между тестами
   - Используйте `beforeEach` для настройки окружения

4. **Пишите понятные сообщения об ошибках**:
   ```typescript
   expect(result).toBe(expected, 'Function should return transformed input');
   ```

5. **Документируйте сложные тесты**:
   - Добавляйте комментарии к сложной логике
   - Объясняйте цель теста и ожидаемое поведение

## Запуск тестов

- **Все тесты**: `npm run test:all`
- **Модульные тесты**: `npm run test`
- **Тесты конфигурации**: `npm run test:config-validation`
- **Тесты конфигурационных параметров**: `npm run test:config-presence`
- **Тесты обработки исключений**: `npm run test:try-catch`
- **Тесты скриптов**: `npm run test:scripts`
- **Конкретный тест**: `npm test -- path/to/test.ts`

## Критерии качества тестов

1. **Покрытие**:
   - Минимум 80% покрытия для всего кода
   - Минимум 90% покрытия для критических компонентов

2. **Скорость**:
   - Быстрое выполнение тестов
   - Тяжелые тесты должны быть отмечены как slow

3. **Читаемость**:
   - Понятные имена тестов
   - Хорошо структурированный код
   - Минимальное дублирование

4. **Поддерживаемость**:
   - Тесты должны быть легко обновляемыми
   - Минимальная зависимость от деталей реализации
   - Фокус на поведении, а не на реализации
