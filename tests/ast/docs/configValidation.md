# Документация теста configValidation.test.ts

## Назначение теста

Тест предназначен для проверки правильного разделения ответственности: доступ к конфигурации и переменным окружения должен осуществляться только в определенных зонах проекта. Основная цель - изолировать работу с конфигурацией от бизнес-логики, чтобы сделать код более поддерживаемым и тестируемым.

## Что проверяет тест

Тест выполняет следующие проверки:
- Сканирует все JavaScript и TypeScript файлы проекта
- Определяет, находится ли файл в разрешенной зоне для работы с конфигурацией
- Выявляет обращения к конфигурации (`config.get()`) вне разрешенных зон
- Выявляет обращения к переменным окружения (`process.env.*`) вне разрешенных зон

## Разрешенные зоны

В текущей конфигурации теста разрешенными зонами для работы с конфигурацией являются:
- `src/config/`
- `scripts/node/`
- `azuro-mapper.ts`

## Пример результата

Если тест обнаруживает нарушения, он выбрасывает исключение с сообщением, содержащим путь к файлу, номер строки и описание нарушения.

### Примеры сообщений об ошибках

1. Неправильное обращение к переменным окружения:
```
src/services/userService.ts:25 - Недопустимое обращение к переменной окружения (process.env.*) вне конфигурационного слоя.
```

2. Неправильное обращение к конфигурации:
```
src/controllers/authController.ts:10 - Недопустимое обращение к конфигурации (config.get(...)) вне конфигурационного слоя.
```

### Рекомендации по исправлению

Если тест обнаружил нарушения, рекомендуется:
1. Перенести доступ к конфигурации и переменным окружения в разрешенные зоны
2. Экспортировать необходимые значения из конфигурационных файлов
3. Импортировать эти значения в файлы, где они используются
4. Использовать внедрение зависимостей вместо прямого обращения к глобальной конфигурации

### Пример исправления

Неправильный подход:
```typescript
// src/services/userService.ts
export function getUserInfo(userId: string) {
  const apiKey = process.env.API_KEY; // Нарушение
  const timeout = config.get('api.timeout'); // Нарушение
  // ...
}
```

Правильный подход:
```typescript
// src/config/api.ts
import { z } from 'zod';

const envSchema = z.object({
  API_KEY: z.string().min(1),
});

const env = envSchema.parse(process.env);

export const apiConfig = {
  apiKey: env.API_KEY,
  timeout: 5000,
};

// src/services/userService.ts
import { apiConfig } from '../config/api';

export function getUserInfo(userId: string) {
  const apiKey = apiConfig.apiKey; // Правильно
  const timeout = apiConfig.timeout; // Правильно
  // ...
}
```

### Почему это важно

Данный паттерн:
1. Делает код более тестируемым (можно мокировать импорт конфигурации)
2. Обеспечивает централизованную валидацию конфигурации
3. Изолирует зависимость от окружения
4. Улучшает читаемость кода (явно видно, какие конфигурационные значения используются)
